# 分類の契約（System One 形式）仕様書（段0 契約）

本仕様書は、自律運用部品 `sigil-vigil-ops` の運用ボットや各判定エージェントが、状況評価・二値判定・多肢選択・段階評価を型安全かつ定量的に行うための「分類の契約（System One 形式）」を厳密に固定する形式契約である。

## 1. 目的とアーキテクチャ

1. **型つき分類インターフェースの標準化**
   - 自由形式のテキスト生成ではなく、「状況テキスト（`state`）」と「型づけされた問い（`questions`）」を与え、確率分布と確信度（`confidence`）を数値として受け取る。
   - 問いの型は System One の体系に準拠し、**Noul（二値判定）**、**Choice（多肢選択）**、**Score（段階評価）** の 3 種をサポートする。
2. **バックエンドの完全隠蔽と不変契約**
   - **暫定バックエンド**: TypeSafe 社の API（`POST https://api.typesafe.ai/v1/systemone`）を使用する。
   - **後段（段3・段4）の自前化**: 後段の開発において、オープンウェイトモデル（小型言語モデルやエンコーダモデル）を用いた自前分類バックエンド、あるいは Sigil ネイティブ推論基盤（C 案）へ差し替える。
   - **契約の不変性**: バックエンドが TypeSafe API から自前実装へ差し替えられても、**本契約で定義するリクエスト・レスポンスの形式、データ構造、確率と確信度のセマンティクスは一切変更しない**。これにより、利用側（`sigil-vigil-ops` のボット等）のコードは一切影響を受けずに稼働し続ける。

---

## 2. API エンドポイント仕様

暫定バックエンドおよび将来の自前バックエンド共通のエンドポイント仕様。

- **メソッド**: `POST`
- **パス**: `/v1/systemone`
- **ヘッダー**:
  - `Content-Type: application/json`
  - `Authorization: Bearer <API_KEY>`（自前化時はローカル認証トークンまたは内部 mTLS）

---

## 3. リクエスト形式仕様（Request Specification）

### 3.1 リクエストボディ構造

```json
{
  "model": "string",
  "state": "string",
  "questions": {
    "<question_id>": {
      "type": "noul | choice | score",
      "...": "型固有のパラメータ"
    }
  }
}
```

### 3.2 共通フィールド仕様

| フィールド名 | 型 | 必須/任意 | 制約・検証規則 | 説明 |
|---|---|---|---|---|
| `model` | string | **必須** | 空文字不可。暫定バックエンドでは `jev-1.13.0` 等、自前化後は `anima-cls-v1` 等を指定。 | 使用するモデル識別名。 |
| `state` | string | **必須** | 1〜32768 文字。空文字不可。 | 判定対象となるコンテキストおよび評価軸。 |
| `questions` | object (map) | **必須** | 1〜50 エントリ。**配列（list）は不可（辞書形式必須）**。 | 問い識別子をキーとする問い定義オブジェクトの辞書。 |

> [!IMPORTANT]
> `questions` は必ず **JSON オブジェクト（辞書形式）** で渡す必要があります。配列形式（`[...]`）で渡すと HTTP 422（Unprocessable Entity）エラーとなります。

#### `state` の記述原則
- `state` の冒頭には、必ず**評価軸・プロジェクト理念・固定方針**を明記すること。
- 後半に、現在判定対象となっている具体的な状況テキスト（イベントログ、メトリクス変化、対象リソースの状態など）を配置する。

---

## 4. 問い型（Question Types）3 種の仕様

### 4.1 Noul（はい/いいえ・二値判定）

状況に対して「はい（yes）」または「いいえ（no）」のいずれであるかを確率で評価する。

#### リクエスト形式
```json
{
  "type": "noul",
  "description": "string (任意: 質問の補助説明)"
}
```

- `type`: `"noul"`（固定）
- `description`（任意）: 1〜500 文字。質問の補足。

#### レスポンス形式
```json
{
  "probabilities": {
    "yes": 0.85,
    "no": 0.15
  },
  "confidence": 0.90
}
```
※ TypeSafe API 実装との互換性のため、`answers[qid]` 直下に `"yes": 0.85, "no": 0.15` が配置される形式、および `probabilities` オブジェクトに内包される形式の双方を正規化して扱えるものとする。

- `yes`: 0.0〜1.0 の実数
- `no`: 0.0〜1.0 の実数（`yes + no == 1.0`）
- `confidence`: 0.0〜1.0 の確信度

---

### 4.2 Choice（多肢選択）

定義された互いに排他的な複数の選択肢候補の中から、最も適合するものを確率分布で評価する。

#### リクエスト形式
```json
{
  "type": "choice",
  "criteria": {
    "<choice_id_1>": "選択肢1の説明・条件",
    "<choice_id_2>": "選択肢2の説明・条件",
    "<choice_id_3>": "選択肢3の説明・条件"
  }
}
```

- `type`: `"choice"`（固定）
- `criteria`: **必須**。2〜20 個の選択肢辞書。
  - キー（`choice_id`）: 1〜64 文字の英数字・アンダースコア・ハイフン。
  - 値: 1〜500 文字の選択肢内容説明。

#### レスポンス形式
```json
{
  "probabilities": {
    "<choice_id_1>": 0.69,
    "<choice_id_2>": 0.21,
    "<choice_id_3>": 0.10
  },
  "confidence": 0.78
}
```

- `probabilities`: 各 `choice_id` に対応する確率（0.0〜1.0、全選択肢の確率の総和は `1.0`）。
- `confidence`: 0.0〜1.0 の確信度。

---

### 4.3 Score（段階評価 / スコアリング）

状況が特定の連続的または段階的な尺度においてどの位置にあるかを評価する。

#### リクエスト形式
```json
{
  "type": "score",
  "scale": {
    "min": 1,
    "max": 5
  },
  "criteria": {
    "1": "極めて健全 / 介入不要",
    "3": "注意 / 警告状態",
    "5": "致命的 / 即時介入必須"
  }
}
```

- `type`: `"score"`（固定）
- `scale`: **必須**。
  - `min`: 最小スコア整数（例: 1）
  - `max`: 最大スコア整数（例: 5 または 10。`min < max`）
- `criteria`: 任意（推奨）。各スコアまたは境界値の評価基準説明。

#### レスポンス形式
```json
{
  "score": 4.20,
  "probabilities": {
    "1": 0.01,
    "2": 0.04,
    "3": 0.15,
    "4": 0.35,
    "5": 0.45
  },
  "confidence": 0.85
}
```

- `score`: 期待値スコア（実数値、`min <= score <= max`）。
- `probabilities`: 各整数スコアの離散確率分布（総和は `1.0`）。
- `confidence`: 0.0〜1.0 の確信度。

---

## 5. レスポンス形式仕様（Response Specification）

### 5.1 全体構造

```json
{
  "model": "string",
  "answers": {
    "<question_id>": {
      "probabilities": {
        "...": "number"
      },
      "confidence": "number (0.00 to 1.00)",
      "score": "number (score型のみ)"
    }
  }
}
```

### 5.2 フィールド一覧・制約

| フィールド名 | 型 | 必須/任意 | 制約・検証規則 | 説明 |
|---|---|---|---|---|
| `model` | string | **必須** | 実行に使用されたモデル識別名。 | 判定を実行したモデル。 |
| `answers` | object (map) | **必須** | リクエストに含まれるすべての `question_id` をキーとして含むこと。 | 各問いに対する回答辞書。 |
| `answers[qid].probabilities` | object | **必須** | 各選択肢/真偽値/スコアの確率。値は `0.0 <= p <= 1.0`。総和が `1.0 ± 0.001` であること。 | 確率分布。 |
| `answers[qid].confidence` | number (float) | **必須** | `0.0 <= confidence <= 1.0`。 | 回答の確信度。 |
| `answers[qid].score` | number (float) | 条件付き必須 | `type == "score"` の場合のみ必須。`scale.min <= score <= scale.max`。 | スコア期待値。 |

## 6. 既存 `POST /v1/systemone`（typesafe-ai）との対応関係

本仕様は、typesafe-ai が提供する System One API のプロトコルに完全に準拠している。

| 項目 | typesafe-ai (`jev-1.13.0`) 実装 | 本契約（sigil-anima-llm）の扱い |
|---|---|---|
| エンドポイント | `POST https://api.typesafe.ai/v1/systemone` | 同一パス `/v1/systemone` を標準とし、自前化時も同一パスを公開する。 |
| 認証 | `Authorization: Bearer $TYPESAFE_API_KEY` | 自前化後も Bearer トークンまたはローカル認証ヘッダーを維持する。 |
| リクエスト `questions` | 辞書形式必須（配列は HTTP 422 エラー） | 辞書形式必須を契約として固定。 |
| 問い型 `noul` | yes/no の確率と confidence を返却 | 完全互換。 |
| 問い型 `choice` | `criteria` 辞書を受け取り各キーの確率と confidence を返却 | 完全互換。 |
| 問い型 `score` | スケール内の期待値スコアと確率分布を返却 | 完全互換。 |
| エラー形式 | `{"error": {"code": "...", "message": "..."}}` | HTTP 400（不正パラメータ）, 422（スキーマ不正）, 500（推論異常）で互換。 |

---

## 7. 形式検証とフェイルセーフ規則

1. **確率分布の妥当性検証**
   - 確率の合計値が $1.0 \pm 0.001$ の範囲外である場合は形式異常として棄却する。
   - 負の確率、または `1.0` を超える値、`NaN`, `Infinity` は即座にエラーとする。
2. **確信度（`confidence`）の判定**
   - クライアント側（`sigil-vigil-ops`）は、取得した回答を採用する前に `confidence` を検証する。
   - 確信度が所定の閾値（例: 0.60 未満）である場合、判定結果を採用せず、デフォルト値へのフォールバックまたは上位層（人間）へのエスカレーションを行う。
3. **バックエンド障害時の動作**
   - タイムアウト（標準 10 秒）または 5xx エラー発生時、クライアントは安全側フラグ（例: 変更を抑止し人間介入を求める状態）を返し、処理を継続しない。
